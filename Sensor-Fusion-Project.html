Project brief

Reuse proven software to test a new language generation.

Starting point

Existing F-22 sensor-fusion software written in Ada 83.

Transition target

A selected portion re-engineered in Ada 95 for the JSF-SFD study.

Industrial team

Boeing Defense and Space Group led the effort; Hughes served as a subcontractor.

Core question

Could Ada 95 and its contemporary toolsets support embedded, real-time avionics work?

Transition path

This was an investigation—not a blind translation.

Legacy baseline Understand the selected Ada 83 sensor-fusion code and its operating assumptions.
Re-engineer Reshape a bounded portion for Ada 95 rather than rewrite an entire aircraft system.
Exercise tools Use the available Ada 95 development environment on representative real-time work.
Record lessons Separate language findings, tool findings, and transition-process findings.

Why Ada 95 mattered

The language makes system boundaries explicit.

Types & subtypes

Express valid values and operating ranges so mistakes are caught near their source.

Packages & private types

Separate stable interfaces from representations that must evolve with hardware.

Tasks & protected objects

Put concurrency and synchronized access into the language model.

Real-time facilities

Represent timing, scheduling, and rendezvous as program semantics.

Representation control

Connect portable logic to device layouts and external interfaces deliberately.

Checked exceptions

Give violated assumptions a visible route instead of allowing silent corruption.

Evaluation frame

Language capability and tool readiness are different questions.

Ada 95 language

  • Can the design express the domain clearly?
  • Can interfaces preserve strong typing?
  • Can concurrency and real-time constraints remain reviewable?
  • Can selected legacy logic be reused without preserving every legacy shape?

Ada 95 toolsets

  • Can compilers and cross-development tools support the target workflow?
  • Can teams debug and integrate representative embedded code?
  • Are libraries, interfaces, and diagnostics mature enough?
  • What training and process changes does adoption require?

The durable lesson

A transition succeeds when it preserves mission knowledge without preserving every accidental constraint of the old implementation.

What to carry forward

Four rules for high-assurance modernization.

Bound the experiment. Use representative mission software, not a toy and not the whole platform.
Separate the evidence. A language may be suitable while a particular generation of tools still needs scrutiny.
Re-engineer intentionally. Reuse validated domain logic, but revisit architecture and interfaces.
Keep timing visible. In sensor fusion, correctness includes delivering a coherent result when it is needed.
